How It Works — PO Governance Engine

Complete logic reference for new category planners · Tool 1 (PO Raise Validation) and Tool 2 (Raised PO Assessment)

Rules in use · VMM PO Governance
Who can do what, how Watch List approvals work, and how today's approved requests are counted.
Sign-in and roles
Everyone signs in with their official email ID. The first password is the default set by the administrator; the tool asks for a new one at first sign-in (at least 8 characters, a letter and a number). Forgotten password: the administrator resets it from the Users screen. Five wrong attempts lock the account for 15 minutes (the administrator can unlock it).
Logins and responsibilities come from the SCR Products file (Brand × MC CD × MRP): Level 1 (Buyer / Sr Buyer / ACM / BFT) and Level 2 sign in as buyers and see their own MCs; Level 3 signs in as Category Head and approves Watch List requests for those MCs. Planners upload data, set parameters and run Tool 2; administrators also manage users.
Watch List approval
A Tool 1 request that comes out as Watch List goes to the Level 3 Category Head of that Brand × MC × MRP, under Approvals. The Category Head approves the full quantity or a smaller one, or rejects with a reason. The buyer sees the decision in Requests. An approved quantity counts against that colour's Max Permissible for the rest of the day; a rejected request counts as 0.
Today's approved requests
Every quantity approved today in Tool 1 (Auto Allow at the confirmed quantity, or a Watch List approved by the Category Head) is treated as pending PO in its delivery month for the same Brand × MC × MRP × Flag × Colour. It is used by:
• Tool 1 — later requests for the same colour see the reduced Max Permissible;
• View Recommendation, Single Concept — shown in the Today's approved column next to Pending PO and deducted from the Max Permissible Qty;
• View Recommendation, Multi Concept — included in the attribute and colour pending PO.
Other colours are not affected: each colour has its own share of the plan.
The count covers today only. From the next day the tool uses the pending POs in the F2 file uploaded by planning: a PO raised and released in SAP appears there and is counted; a request that was never raised is not. Raise the PO in SAP on the same day you validate it.
Requests, History, Video and Feedback
• Requests — today's checks on your MCs, with the decision, approved quantity and approval status.
• History — earlier days, by date range (record only; it does not change any calculation).
• Video — a walk-through of every result type and View Recommendation.
• 💬 Feedback (top of the page) — report a problem or suggest an improvement; the administrator reviews every entry.
Purpose
Why does this tool exist?
Every PO raised without a demand check risks overstock — money locked in slow-moving inventory, forced markdowns, and lost shelf space for better sellers. This tool runs the same logic the Planning team uses — sell-through benchmarking and rolling stock cover — so every category planner can validate in under 30 seconds before committing to a vendor.

Two tools, one continuous loop: Tool 1 prevents bad POs from being raised. Tool 2 catches POs that were correct when raised but have since gone stale due to poor sell-through.
🛡 Tool 1 — PO Raise Validation
When: Before you raise a new PO
Question: Should I raise this colour at this quantity?
Input: Generic Material + Colour + Delivery Month + Proposed Qty
Engines: Multi Concept MRP (peer ranking) or Single Concept MRP (stock cover)
Outcomes: Allow · Reduce Qty · Hold · Watch List · Block
🔍 Tool 2 — Raised PO Assessment
When: Periodically — review all open released POs
Question: Should existing POs be retained, reduced, or cancelled?
Input: Batch upload of released PO file
Engines: Same Multi Concept MRP and Single Concept MRP, applied to released qty
Outcomes: Retain · Reduce Qty · Cancel · Watch List
Routing — How the system decides which engine to use
Two-step engine routing — runs on every article
S1 Universe Master check — Is the Generic Material in the Universe Master? (Key: Brand × MC × MRP × BOGO × Generic Material)
✓ Found → Single Concept MRP (Colour STR). No further check needed.
✗ Not found → Go to Step 2.
S2 CY BSR check (Tool 1 only) — Is the Generic Material in the Current Year Best Seller Report?
✓ In CY BSR → Multi Concept MRP (Peer ranking — True Repeat or BOBs)
✗ Not in BSR → Auto Allow (Genuinely new article — no sell-through history)
Note: Tool 2 skips Step 2 — no UM match goes straight to Multi Concept MRP.

Example: GM 1112044700, colour LGY — both appear in Mens SS26 BSR with WOF=23w → True Repeat → peer ranking. | GM 1112044700 in BSR but raising in new colour → BOBs → parent style check first.
2
BOBs — Parent Style Check (only for BOBs option type)
Before allowing a new colour, check if the parent style is a healthy seller
For BOBs, we look at all existing sibling colourways (same GM, other colours) in the BSR. We filter to siblings with WOF ≥ 4 weeks. These are ranked in the full peer group (Brand × MC × MRP × Flag) by per-day STR%.

If sibling qualifies: best-ranked sibling's quartile determines decision.
If no sibling qualifies: fall through to rank the parent style directly.
No siblings at all: Auto Allow — new colourway with no comparable history.
Sibling Q2/Q1 → AllowSibling Q3 below avg + both gates pass → AllowSibling Q3 below avg + gate fails → Watch ListSibling Q4 + both gates pass → Watch ListSibling Q4 + gate fails → Block
3
BSR Reference — Which data to rank against?
CY BSR first — LY SS+AW combined if CY pool is too thin
Primary: CY BSR (SS26) — current season data.
Peer group: Brand × MC × MRP × Flag.
Fallback: If CY peer group has fewer than 5 qualifying styles (after WOF ≥ 4w filter), system merges LY BSR SS25 + LY BSR AW25 into one combined pool.

Decision reason always states the data source — e.g. "ranks Q4 in 21 styles (LY BSR SS+AW combined)".
Example: MC 113030008, MRP ₹79, Normal — only 1 style in CY BSR (WOF=9w). Peer min=5 not met → fallback season BSR used → 21 styles available.
4
Peer Ranking — Filter → Rank → Quartile → Peer Average Guard
1
Filter — WOF ≥ 4 weeks
Only articles with at least 4 weeks on floor are included in peer pool. If your article itself has WOF < 4w → Auto Allow (insufficient history).
2
Rank — Per-Day Sell-Through %
Per-Day STR% = Total Sell-Through % across 3 weeks ÷ 21 days. Normalises for time — directly comparable regardless of when the style launched. Full WOF-filtered pool used — no IQR removal.
3
Quartile — Where does the article land?
Q4 (bottom 25%) = slowest · Q3 (25-50%) = below median · Q2 (50-75%) = healthy · Q1 (top 25%) = best sellers. Full pool used — genuine slow/top performers visible.
4
Border Zone — Single 10% Threshold for Q4 and Q3
When an article ranks Q4 or Q3 AND PDSTR is below peer average, a border zone check runs before the hard decision:

Threshold (Q4 & Q3): If gap from peer avg ≤ 10% → border zone applies.

Q3 + gap ≤ 10% → Allow
Q4 + gap ≤ 10% → Watch List
Q4/Q3 + gap > 10% → hard decision stands

Configurable: S.params.borderTolerance = 10
Example (True Repeat — Q4 Block): GM 1112044700, LGY · MC=112010016, MRP ₹699, Normal · PDSTR=1.80%/day. Peer pool: 28 styles pass WOF≥8w. Ranked 4th from bottom out of 25 = 16th percentile → Q4. Peer avg=2.21%/day. Our 1.80% < 2.21% → Block.
🚨 Absolute Block Override — fires regardless of quartile
Rule: If Per-Day STR% < 1%/day AND Weeks on Floor ≥ 4 weeks → Block immediately, regardless of Q2/Q1 ranking.

Why: A quartile ranking is relative — an article can rank Q2 in a category where all articles are slow. The Absolute Block is an absolute threshold that catches any article selling at less than 1% of stock per day after 4+ weeks on the floor. This is an extremely poor seller by any standard.

Where it applies: Both Tool 1 (before raising) and Tool 2 (on existing raised POs). Applied after quartile ranking — even Q1 articles are blocked if they breach this threshold.
Final Decision Outcomes — Multi Concept MRP, Tool 1
✓ Allow / Auto Allow
New Option (no history) · WOF < 4w (insufficient history) · No BOBs siblings found · Q2 or Q1 · Q3 PDSTR ≥ peer avg · Q3 below avg with gap ≤ 10% (border zone) · Q4 PDSTR ≥ peer avg
👁 Watch List
Q3 below avg with gap > 10% · Q4 PDSTR ≥ peer avg · Q4 below avg with gap ≤ 10% (border zone — softened from Block)
🚫 Block
Q4 below avg with gap > 10% · Absolute Block override (PDSTR < 1%/day AND WOF ≥ 4w)
Border Zone parameter:  Threshold = 10% below peer avg (applies equally to Q4 and Q3). Configurable in S.params.borderTolerance.
Single Concept MRP is triggered when: The Generic Material is found in the Universe Master. It answers: "If I add this proposed quantity to existing stock and open POs, how many days of demand does that cover?"
1
Gate — Colour Mix % Check
Is this colour a meaningful share of the MC's demand?
Formula (primary — when F3 has daily Day 1..Day N columns): Colour Mix % = SUM(Colour daily sales) ÷ SUM(MC total daily sales), both over the last 45 days

Formula (when F3 has monthly columns only): Colour Mix % = Colour avg monthly sales ÷ MC total avg monthly sales (last N=2 months)

If Mix % < 2% → Watch List. Likely broken sizes (only S/XL left). STR not computed.
If Mix % ≥ 2% → Proceed to STR computation.
Example: MBU colour · MC 112020003 · Apr+May avg = 24,336/mo ÷ MC avg 185,587/mo = 13.11% → passes gate.
2
Opening Stock (F1) — Today's physical stock
Sum ALL F1 rows matching KEY-3 (Brand × MC × MRP × Flag × Colour)
F1 is uploaded daily. It already reflects all sales consumed up to today. Multiple rows exist for different RDC locations — all are summed.

Op Stock = SUM of all F1 rows where KEY-3 matches
Example: MBU has 2 F1 rows: Row 1 = 44,128 · Row 2 = 43,384 → Op Stock = 87,512 units.
3
Forward Stock Build — Roll stock to Window Start (Delivery Month + 1)
Month by month: add POs, subtract demand, arrive at opening stock at the STR window start
Starting from F1 stock (as-of-today), walk forward month by month to the Delivery Month, then one month further to Day 1 of DM+1 (the STR window start). Each month: add F2 POs arriving that month, subtract colour demand (F4 × Mix%). Proposed PO added in DM month only.

Current month: F1 already reflects sales up to today, so only remaining days of current month's demand are subtracted.

Current month demand = (F4 × Mix%) × (remaining days ÷ days in month)
Month close = MAX(0, Open + Existing POs − Colour Demand)
Example (today=Jun 28, DM=Jul 2026): F1=87,512. Jun remaining=2 days. Jun demand=14,530×2/30=969. Jun PO=+722. Stock at Jul 1 = 87,512+722−969 = 87,265.
4
60-Day Window Demand & Daily Rate
How fast does this colour sell? Measured from Day 1 of Window Start (DM+1) over D=60 days
Sum colour demand (F4 × Mix%) across the next 60 calendar days from Day 1 of the window start. Months prorated if D days falls partway through.

Daily Rate = 60-day window demand ÷ 60

Demand-driven only. Stock and POs do not affect daily rate. Rate changes when delivery month changes (different F4 values) or when D changes (different accumulation window).
Example (DM=Jul 2026, D=60): Jul colour demand=10,127 (31d). Aug(29d)=13,485×29/31=12,615. Total=22,742. Daily Rate=22,742÷60=379/day. (This example uses D=60 to keep the arithmetic simple; the tool uses the D set in Parameters, shown in the table above.)
5
Colour STR — How many days does stock last?
STR = Stock ÷ Daily Rate. Compare to Effective Threshold = T×(1+Buffer%) (default 75d × 1.05 = 78.75d).
Colour STR = (Stock at Window Start (DM+1) ÷ 60-day demand) × D

STR ≤ T×(1+Buffer%) (default 78.75d): Stock absorbed within threshold → Allow.
STR > T×(1+Buffer%): Exceeds threshold → compute Max Permissible Qty.
Max Permissible formula uses the BUFFERED threshold, T×(1+Buffer%) — the same effective threshold used for the breach test, not raw T. This keeps the breach test and the recommended quantity consistent with each other.
Example: Stock at Jul 1=87,265. 60-day demand=22,742. STR=(87,265÷22,742)×60=230d >> effective threshold 78.75d (T=75d + 5% buffer) → HOLD.
6
Max Permissible Qty & Decision
How much CAN you raise without breaching the effective threshold?
Max Permissible = MAX(0, T×(1+Buffer%) × Daily Rate − Stock at Window Start (DM+1))

Max Permissible = 0: Existing stock already exceeds T×(1+Buffer%) × Daily Rate → Hold.
Max Permissible > 0: the Confirm Final Quantity pop-up opens, showing the proposed quantity and the Max Permissible, pre-filled with the Max Permissible. The buyer enters the quantity to raise (up to the Max Permissible) and confirms → Auto Allow at that quantity. Don't Raise records 0.
The confirmed quantity counts against the same colour's Max Permissible for every later request that day (all users).
Example (using Effective T=78.75d, Daily Rate=379/day, Stock=87,265): Max Perm = MAX(0, 78.75×379−87,265) = MAX(0, −57,419) = 0 → Full Hold. Nothing can be raised.
👁 Watch List
Colour Mix % < 2% — broken/cut size. Not enough mix to compute reliable STR.
✓ Auto Allow (at the confirmed quantity)
Max Permissible > 0. The buyer confirms a quantity up to the Max Permissible in the pop-up; that quantity is allowed. When the proposed quantity is above the Max Permissible, only the Max Permissible (or less) can be confirmed — raise in SAP only the confirmed quantity.
🔴 Hold — Don't Raise
STR > T×(1+Buffer%) AND Max Permissible = 0. Existing stock already covers more than the effective threshold (default 78.75 days). No headroom for any new quantity.

Tool 2 Single Concept MRP applies the same Colour STR logic as Tool 1 Single Concept MRP — but assesses an already-raised PO. The released PO qty is already in F2, so the system assesses whether retaining, reducing, or cancelling makes sense.
Tool 1 — Prospective
Proposed PO qty injected into the chain in the DM month.
Window starts Day 1 of (Delivery Month + 1).
Decision: Allow / Reduce / Hold.
Tool 2 — Retrospective
Released PO already in F2 — not injected separately.
Window starts Day 1 of (Delivery Month + 1) — same rule as Tool 1.
Decision: Retain / Reduce Qty / Cancel.
1
F1 Op Stock — same rule as Tool 1
SUM all F1 rows for KEY-3. Multiple RDC rows summed. F1 reflects sales up to today.
2
Colour Mix % Gate
Same as Tool 1: daily F3 data used when present (SUM Day1..DayN ÷ 45), else monthly average (last N=2 months). Mix% < 2% → Watch List.
3
Pre-roll to window start (Delivery Month + 1)
Current month: remaining days demand only. Future months: full month demand. Released PO already in F2 — no separate injection.
4
60-day window & Daily Rate
Same formula as Tool 1: SUM of colour demand (F4 × Mix%) over next 60 days from window start ÷ 60.
5
Colour STR & Max Permissible
STR = (Stock at window start ÷ 60-day demand) × 60. Breach if STR > T×(1+Buffer%) (Effective T = 78.75d by default). Max Permissible = MAX(0, T×(1+Buffer%) × Daily Rate − Stock w/o this PO) — uses the same buffered Effective T as the breach test. Stock already includes released PO via F2, so it's subtracted back out before this calculation.
✓ Retain
STR ≤ Effective T (T×(1+Buffer%), default 78.75 days). Released PO is within cover threshold — keep it.
↓ Reduce Qty
STR > Effective T but Max Permissible > 0. Amend PO down to Max Permissible units. Cancel the balance.
❌ Cancel
STR > Effective T AND Max Permissible = 0. Existing stock (without this PO) already exceeds the effective threshold (default 78.75 days). Cancel entire released PO quantity.
Example (Cancel): GM 1112044799, MBU, released PO 722 units, DM Jun 2026. Op Stock=87,512. Mix%=13.11%. Jun remaining=969 units demand. Stock at Jul 1=87,265. 60-day demand=22,742. Daily Rate=379/day. STR=87,265÷379=230d >> effective 78.75d (T=75 + 5%). Max Perm=MAX(0,78.75×379−87,265)=MAX(0,−57,419)=0 → Cancel.

Multi Concept MRP — Colour/GM Recommendation Engine
What should this Reduce/Cancel line switch to instead? (the "Option 1/2/3" columns)
Driven by
Attribute Relevance Master
For each Brand × MC × MRP × Flag bucket, this file names which product attribute is the meaningful lens for ranking within that bucket — Style, Fit, Product Material, Design, or Colour-only (no attribute tier at all, judge by colour directly). Article Master supplies each Generic Material's actual value for whichever attribute is named.
1
Rank attribute values by deviation
Within the MC×MRP bucket, each attribute value (e.g. each Style) is ranked by Sale Mix% − Stock Mix% deviation — attribute values selling faster than they're stocked rank first.
2
Rank colours within the best attribute value
Inside the top-ranked attribute value, colours are ranked by their own colour-level STR (stock-cover days) — lowest (fastest-moving) first.
3
Cross-verify each candidate against BSR
A candidate colour only gets recommended if it can be genuinely confirmed as Q1 (top quartile) in the Best Seller Report — falling back to Q2 only if no Q1 candidate clears. This is the same BSR peer-ranking engine Tool 1/Tool 2's own decisions use, just run in reverse to find a good option instead of judging the current one.

Fallback path — when the fuller detail isn't shown
If any of these apply for that row's own MC×MRP×Brand×Flag bucket, the recommendation instead falls back to plain colour-level STR ranking across the whole bucket — no quartile or PDSTR shown, since that data genuinely wasn't verified for this bucket:
• No entry in Attribute Relevance Master for that exact Brand×MC×MRP×Flag combination
• The dimension listed is "Colour-only"
• Nothing in that bucket could actually be confirmed as Q1 or Q2 in the BSR

This is why two Reduce/Cancel rows can show different Option formats — GM / COLOUR (Q1, STR 10d, PDSTR 3%/day) — Style vs the simpler GM / COLOUR (STR 61d) — depending on what's actually available for each row's own bucket, not a bug.
Exploration only — Recommendation screen
On the live Recommendation drill-down (click a row after a decision is made), a dropdown next to "Dimension: X" lets you manually switch to any of the 4 attributes to see what the ranking and recommendations would look like under a different lens. The dimension Attribute Relevance Master actually calls for is always marked "(Relevant)" and is what's shown by default. Switching it only changes what that screen displays — it never changes the row's actual stored decision.
